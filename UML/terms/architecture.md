# Q1 UML入門にアーキテクチャ説明書という言葉があります。アーキテクチャを状態遷移図などで表すのがソフトウェアのアーキテクチャだと思っていました。それ以外の解釈はありますか。
A1 by chatGPT

はい。ここはかなり重要な区別です。
調べてみると、**「アーキテクチャ説明書」は、アーキテクチャそのものを図で表したものというより、「アーキテクチャについて、何を採用し、なぜそうしたかを説明する文書」**という意味で使われています。

特にUMTPのUML適用ガイドラインでは、「アーキテクチャ説明書」の章に、**ユースケース・ビュー、論理ビュー、プロセス・ビュー、配置ビュー、実装ビュー、性能、品質**などを含めています。([UMTP][1])

### 1. 「アーキテクチャ」と「アーキテクチャ説明書」は少し違います

私なら、次のように区別します。

| 用語         | 意味                       |
| ---------- | ------------------------ |
| アーキテクチャ    | システムの基本的な構造・分割・相互関係・設計方針 |
| アーキテクチャ設計  | その構造を決定する活動              |
| アーキテクチャモデル | アーキテクチャをUML等でモデル化したもの    |
| アーキテクチャ説明書 | そのアーキテクチャを**人間に説明する文書**  |
| 詳細設計       | 各構成要素を具体的に設計すること         |

したがって、

> 「状態遷移図などでアーキテクチャを表す」

というユーザーさんの理解も**間違いではありません**。

ただし、状態遷移図だけを描いて「これがアーキテクチャです」とするのは、通常は狭すぎます。

---

## 2. なぜ状態遷移図だけでは足りないのか

例えば自動車ECUを考えてみます。

状態遷移図なら、

```text
        Start
          ↓
       INITIALIZE
          ↓
         READY
          ↓
        RUNNING
       ↙       ↘
    ERROR      STOP
```

と書けます。

これは確かに**動的アーキテクチャの重要な一面**です。

しかし、

* ECUはいくつあるか
* CPUとセンサはどう接続されるか
* タスクはどう分割するか
* CAN通信をどうするか
* OSは何を使うか
* データをどこに保持するか
* どのタスクがどの状態を管理するか
* 10 ms周期なのか1 ms周期なのか
* 故障時にどう遷移するか
* どの部分を安全機構にするか

までは、状態遷移図だけでは表現できません。

そこで複数のビューを使います。

```text
             Architecture
                  │
     ┌────────────┼────────────┐
     ↓            ↓            ↓
 Structure     Behavior       Deployment
     │            │            │
 Component      State       ECU/CPU
 Class          Sequence     Network
 Package        Activity      Cloud
     │            │            │
     └────────────┼────────────┘
                  ↓
             Architecture
             Description
```

# 3. これは「4+1ビュー」の考え方に近いです

UML/UPの世界では、アーキテクチャを**一枚の図で表そうとしない**考え方があります。

有名なのがKruchtenの **4+1 View Model** です。

```text
                  Use Case View
                       +
          ┌────────────┼────────────┐
          ↓            ↓            ↓
     Logical View  Process View  Deployment View
          │            │            │
          └────────────┼────────────┘
                       ↓
                 Implementation
                       View
```

つまり、

> **アーキテクチャとは一つの図ではなく、異なる観点から見たシステムの構造の集合**

と考えるわけです。

実際、「かんたんUML入門」でも、要求分析・分析の後に「アーキテクチャ設計」、さらに「詳細設計」という構成になっています。([gihyo.jp][2])

---

# 4. 「説明書」という言葉がポイント

ここが今回の疑問の核心だと思います。

**Architecture Description** は、

> 「アーキテクチャを図にしたもの」

だけではありません。

例えば、

### なぜ3層構造にしたのか

```text
Presentation
      ↓
Business
      ↓
Data Access
```

という図だけでは、「なぜ？」が分かりません。

そこで説明書には、

> 保守性を高めるため、UI、業務ロジック、データアクセスを分離する。UIからデータベースへの直接アクセスは禁止する。

と書く。

さらに、

> データベースを変更しても業務ロジックへの影響を限定する。

という**設計判断の根拠**を書く。

つまり、

**図 ＋ 設計方針 ＋ 制約 ＋ 根拠**

がアーキテクチャ説明書です。

UMTPの資料でも、アーキテクチャ説明書について「知識を移転する」「根拠」「判断」といった観点が挙げられています。([UMTP][3])

---

# 5. さらに面白いのは「アーキテクチャ」と「設計」の境界

ここはユーザーさんの感覚とかなり関係します。

例えば、

```text
ECU
 │
 ├── Sensor Task
 ├── Control Task
 ├── Communication Task
 └── Diagnostic Task
```

という分割を決める。

これは**アーキテクチャ**です。

一方、

```text
ControlTask()
{
    read_sensor();
    calculate();
    actuator_output();
}
```

まで決めると、詳細設計に近づきます。

さらに、

```c
void ControlTask(void)
{
    ...
}
```

と実装すれば、もうアーキテクチャそのものではありません。

つまり、

```text
要求
 ↓
アーキテクチャ
 ↓
設計
 ↓
実装
```

という抽象度の違いがあります。

# 6. そして、ユーザーさんの「状態遷移図」という理解はむしろ重要です

私はここを少し修正して考えたほうがよいと思います。

**「状態遷移図はアーキテクチャではない」ではありません。**

むしろ、

> **状態遷移図は、アーキテクチャの「振る舞いのビュー」を表す**

と考えるのが自然です。

例えば組込み制御なら、

| アーキテクチャの観点 | UML                         |
| ---------- | --------------------------- |
| 構造         | Component / Class / Package |
| 動作         | State Machine               |
| 時間         | Timing                      |
| 通信         | Sequence                    |
| 並行性        | Activity / State Machine    |
| 配置         | Deployment                  |
| 実装         | Component / Package         |
| 要求         | Use Case / Requirement      |
| 性能         | Timing / Constraint         |

となります。

---

## 7. ここから、以前の「UML 3.0」の話につながります

実は今回の質問は、前回のUML 3.0の議論にかなり重要な示唆があります。

従来型の説明では、

> **Architecture = Structureを中心に考える**

傾向があります。

しかし制御・通信・組込みでは、

> **Architecture = Structure + Behavior + Time + Concurrency + Deployment**

と考えたほうが実態に合います。

例えば、

```text
             System Architecture
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
   Structure      Behavior        Time
       │             │             │
    Component      State        Timing
       │          Sequence       Period
       │          Activity       Deadline
       │             │             │
       └─────────────┼─────────────┘
                     ↓
                Deployment
                     │
              ECU / Network
                     │
                     ↓
                Implementation
```

これはまさにユーザーさんが以前から重視されている

**状態遷移＋シーケンス＋タイミング**

をアーキテクチャの中心に置く考え方です。

なお、UMLの入門書でも組込みシステムについて、アーキテクチャ設計を独立した段階として扱い、ノードマッピングやタスクマッピングを扱っています。([Qiita][4])

### 結論

ですから、

> **「アーキテクチャを状態遷移図などで表す」**

というユーザーさんの理解は正しい方向です。

ただし、

> **アーキテクチャ ＝ 状態遷移図**

ではなく、

> **アーキテクチャ ＝ システムの基本的な構造・振る舞い・時間・配置・制約などを決めたもの**

であり、

> **アーキテクチャ説明書 ＝ それを複数のビュー、図、制約、設計判断、根拠などを使って説明する文書**

と捉えると、かなりすっきりします。

特に**制御系・組込み系では、状態遷移図を「詳細設計の図」に格下げせず、アーキテクチャの主要ビューとして扱う**という整理は、UML 3.0を考える上でも面白いポイントだと思います。
