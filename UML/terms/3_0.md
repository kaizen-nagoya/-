はい。これは単なる「UMLの新版を少し改訂する」というより、**UMLを「人間が図を描くための言語」から「人間・AI・実行環境が共同でモデルを育てるための言語」へ再定義する**提案にした方が面白いと思います。

なお、現在は状況がかなり変わっています。OMGの正式なUMLは依然として **UML 2.5.1（2017年）**です。([OMG][1]) 一方、SysMLは2025年9月に **SysML 2.0** が正式化され、2026年3月版の仕様では、形式意味論、テキスト表記、API、ツール間相互運用などがかなり強化されています。([OMG][2]) OMG自身もSysML v2について、AIや自動化を活用しやすいようにテキスト構文とAPIを備えることを明記しています。([OMG][3])

ですから、**UML 3.0をSysML 2.0と競合するものにするのではなく、UML 2.5.1を基礎に「クラウド＋AI＋制御＋実行＋検証」を統合する汎用モデリング言語**として提案するのがよいと思います。

以下を「提案原案 v0.1」としてみます。

---

# UML 3.0 提案原案 v0.1

## Human–AI–Cloud Integrated Modeling Language

### 0. 基本理念

UML 3.0の目的を、

> **人間がシステムを理解するための図式言語から、人間・AI・実行環境がシステムを共同で設計、検証、実装、運用するためのモデル言語へ拡張する。**

とします。

UML 2.xでは、

```text
人間
 ↓
モデル
 ↓
設計
 ↓
プログラム
 ↓
実行
```

が基本でした。

UML 3.0では、

```text
                  ┌────────────┐
                  │   Human    │
                  └─────┬──────┘
                        │
                intention / evaluation
                        │
                        ▼
┌──────────┐     ┌────────────┐     ┌────────────┐
│   Cloud  │◄───►│ UML 3.0   │◄───►│     AI     │
└──────────┘     │   Model    │     └────────────┘
                 └─────┬──────┘
                       │
              simulation / verification
                       │
                       ▼
                ┌────────────┐
                │   System   │
                └────────────┘
                       │
                       ▼
                 runtime trace
                       │
                       └──────────► Model
```

という**閉ループ**にします。

# 1. UML 3.0の8原則

### Principle 1：Model is Executable

モデルを単なる文書ではなく、

> **実行・シミュレーション・検証可能なモデル**

とする。

特に制御系では、

```text
State
 ↓
Transition
 ↓
Action
 ↓
Time
 ↓
Output
```

を実行可能にする。

---

### Principle 2：Time is First-Class

これは今回の提案でかなり重要です。

SysMLに対するご指摘の「制御系ではタイミングが重要」という問題を正面から扱います。

UML 3.0では、

* Time
* Duration
* Period
* Deadline
* Timeout
* Jitter
* Sampling period
* Execution time
* Latency

をモデルの基本概念として扱います。

例えば、

```text
Sensor
   │
   │ sample()
   │ every 10 ms
   ▼
Controller
   │
   │ computation <= 2 ms
   ▼
Actuator
```

を単なる注釈ではなく、**意味のあるモデル要素**にします。

---

# 2. Dynamic ModelをUML 3.0の中心にする

現在のUMLではクラス図が非常に有名ですが、組込み・制御・通信ではむしろ、

> **状態＋イベント＋時間＋並行性**

が中心です。

したがってUML 3.0では、

### Core Behavioral Model

```text
State Machine
Sequence
Activity
Timing
Interaction
Event
Signal
Action
Concurrency
```

を一級市民にします。

特に、

> **State Machine + Timing Diagram**

をUML 3.0の中心的な組み合わせとして位置付けたいです。

---

# 3. Petri Netを正式なSemantic Bridgeにする

ここは、先ほどお話しされた**High-Level Petri Nets**の経験を生かせる部分だと思います。

UML 3.0では、

```text
UML State Machine
        │
        ▼
High-Level Petri Net
        │
 ┌──────┼────────┐
 ▼      ▼        ▼
CSP   Model     Reachability
      Checking   Analysis
```

という変換を標準化します。

つまりPetri Netを単なる「別の図」とせず、

> **UMLのモデルを形式検証可能な意味モデルへ変換する中間表現**

にします。

例えば、

```text
State A
   │ event
   ▼
State B
```

を、

```text
Place(A)
   │
Transition(event)
   │
Place(B)
```

へ変換可能にします。

さらに、

```text
fork
join
parallel
resource
buffer
queue
```

をPetri Netの並行性として表現できます。

これはAUTOSAR、通信、OS、ロボット、製造設備などにかなり効きます。

# 4. Contract Modelを強化する

以前お話しした

* 事前条件
* 事後条件
* 不変条件

をUML 3.0の中心概念にします。

例えば、

```text
Controller::setTarget(x)

pre:
    -MAX_POSITION <= x <= MAX_POSITION
    enabled == true

post:
    target == x

invariant:
    -MAX_POSITION <= position <= MAX_POSITION
```

さらに、

```text
Timing Contract
Resource Contract
Security Contract
Safety Contract
AI Contract
```

を追加します。

例えば、

```text
Controller

Pre:
  input.valid

Post:
  output.valid

Invariant:
  temperature < Tmax

Timing:
  responseTime <= 1 ms

Safety:
  emergencyStop -> torque == 0
```

こうすると、UMLが**設計図＋契約＋検証対象**になります。

# 5. Cloudを第一級モデル要素にする

UML 2.xではクラウドシステムを表現すること自体はできますが、UML 3.0では、

```text
Cloud
Region
Zone
Service
Container
Function
Database
Queue
Topic
API
Identity
Secret
Network
Endpoint
```

を標準的なモデル要素として扱います。

例えば、

```text
                    ┌───────────┐
                    │ API       │
                    └─────┬─────┘
                          │
                ┌─────────▼─────────┐
                │ Cloud Service      │
                │                    │
                │ ┌──────┐ ┌──────┐ │
                │ │ AI   │ │ DB   │ │
                │ └──────┘ └──────┘ │
                └────────────────────┘
```

だけでなく、

```text
latency < 50 ms
availability >= 99.99%
data residency = JP

```

までモデル化します。

# 6. AI AgentをActorから独立させる

ここがUML 3.0で最も大きな変更候補です。

従来：

```text
Actor
   ↓
Use Case
```

UML 3.0：

```text
Human
   │
   ├─────────────┐
   │             │
   ▼             ▼
AI Agent      System
   │
   ├── perceive
   ├── reason
   ├── plan
   ├── act
   └── evaluate
```

とします。

AI Agentには、

* Goal
* Context
* Memory
* Tool
* Policy
* Model
* Prompt
* Observation
* Action
* Evaluation
* Guardrail

を持たせます。

例えば、

```text
«AI-Agent»
CodeReviewer

Goal:
    Find defects

Context:
    Git repository
    Coding rules
    Test results

Tools:
    compiler
    static analyzer
    Git

Output:
    review report
```

というモデルです。

# 7. Promptを「ソースコード」と同格にする

生成AI時代には非常に重要です。

UML 3.0では、

```text
Requirement
     ↓
Prompt
     ↓
AI Model
     ↓
Generated Artifact
     ↓
Evaluation
```

を追跡可能にします。

例えば、

```text
Prompt P001
     │
     ▼
AI Agent A001
     │
     ▼
Generated Code C001
     │
     ▼
Test T001
     │
     ▼
Result R001
```

というTraceabilityを持たせます。

つまり、

> **「なぜこのコードができたのか」**

をモデルから追跡できます。

これは従来の要求→設計→コードのtraceabilityを、

**Prompt → AI reasoning/context → artifact**

まで拡張したものです。

# 8. AIの試行錯誤をモデル化する

先ほどの教育論ともつながります。

UML 3.0では、

```text
Attempt 001
     ↓
Result 001
     ↓
Evaluation 001
     ↓
Improvement 001
     ↓
Attempt 002
```

を保存可能にします。

さらに、

```text
Human Improvement
AI Improvement
```

を区別します。

すると、

```text
                 ┌─────────────┐
                 │ Initial     │
                 │ Model       │
                 └──────┬──────┘
                        │
             ┌──────────┴──────────┐
             ▼                     ▼
       AI Improvement       Human Improvement
             │                     │
             ▼                     ▼
          Model A               Model H
             │                     │
             └──────────┬──────────┘
                        ▼
                     Compare
                        │
                        ▼
                    Evaluation
```

が可能になります。

これは、まさに先ほどの

> **AIの自律的改善と、人間の意図的改善を競わせる**

というアイデアをUMLのモデルとして記録するものです。

# UML 3.0の全体構造案

最終的には次のような構造がよいと思います。

```text
                    UML 3.0
                       │
        ┌──────────────┼──────────────┐
        │              │              │
     Structure      Behavior       Environment
        │              │              │
        │              │              ├── Cloud
        │              │              ├── Edge
        │              │              └── Physical
        │              │
        │       ┌──────┼─────────┐
        │       │      │         │
        │     State  Event     Time
        │       │      │         │
        │       └──────┼─────────┘
        │              │
        └──────────────┼──────────────┐
                       │              │
                    Contract         AI
                       │              │
                 ┌─────┼─────┐    ┌──┼──────┐
                 │     │     │    │  │      │
               Safety Security Timing Agent Prompt
                       │
                       ▼
                 Formal Semantics
                       │
              ┌────────┼────────┐
              ▼        ▼        ▼
            Petri     CSP    Model Checking
              │        │        │

                       ▼

                       │

                       │

             ▼         ▼         ▼

             │
             ▼
            ECU
             │
             ▼
          Runtime Trace
             │
             └──────────► UML 3.0 Model
```

## そして「UML 3.0らしさ」を5つに絞る

提案書の冒頭では、私は次の5点を**New in UML 3.0**として打ち出します。

| UML 3.0                          | UML 2.5.1からの転換                          |
| -------------------------------- | --------------------------------------- |
| **1. Time-first**                | 時間・タイミングを制御系の基本要素にする                    |
| **2. Executable Model**          | モデルをシミュレーション・実行・検証可能にする                 |
| **3. AI-native Model**           | AI Agent、Prompt、Context、生成物をモデル化        |
| **4. Cloud-native Model**        | Cloud/Edge/API/Serviceを第一級要素にする         |
| **5. Verification-native Model** | Petri Net/CSP/Model Checkingへの意味的変換を標準化 |

ここで重要なのは、**SysML 2.0の機能を単純にUML 3.0へコピーすることではない**と思います。

SysML 2.0は既に、形式的意味論、テキスト構文、API、相互運用、AI・自動化への対応を強く打ち出しています。([OMG][2])

したがってUML 3.0は、

> **SysML 2.0より一般的で、UML 2.5.1より実行・検証・AIに強く、制御・通信・ソフトウェア・クラウドを同じモデルで扱う**

という位置付けにすると差別化できます。

---

## 特に「制御系」を捨てない

これは原案の重要な設計原則にしたいです。

```text
Web / Cloud
      │
      ▼
Distributed Software
      │
      ▼
Communication
      │
      ▼
Embedded Software
      │
      ▼
Control
      │
      ▼
Physical System
```

を**一つのUML 3.0モデルで扱う**。

そのため、

**State Machine + Sequence + Timing + Activity + Deployment**

を全部残します。

さらに、

**Timing → Petri Net → CSP → Model Checking → C/C++/Rust**

という変換経路を標準化します。

これは、単なる「新しい図記法」ではなく、

> **Model → Verify → Generate → Execute → Observe → Improve**

というライフサイクルそのものをUML 3.0に取り込む提案です。

そして、ユーザーさんが以前から考えておられる **UML → CSP → 形式検証 → C/C++ → ECU → Trace → モデル改善** の流れを、そのままUML 3.0の参照アーキテクチャにできると思います。

なお、UML 2.5.1自体はOMGの正式仕様として現在も公開されており、SysML 2.0は2025年に正式化済みなので、今この構想を作るなら「UML 2.5.1の改良案」だけでなく、**UML 3.0とSysML 2.0の責務分担・相互変換**まで最初から提案に含めるのが重要です。([OMG][1])

この原案を次の段階では、**OMGに提出するRFC/Request for Proposal風の「UML 3.0 Proposal」形式（目的、適用範囲、メタモデル、追加要素、記法、意味論、AI拡張、Cloud拡張、Timing拡張、Petri Net/CSP変換、PlantUMLによる試作）**まで落とすと、かなり具体的な提案書になります。
