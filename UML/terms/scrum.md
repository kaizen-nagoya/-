# Q1 スクラムというアジャイルの一つの流派があります。従来ウォータフォールや、CMMで開発プロセスを定義していた人たちが、アジャイルに移行する際の、よい指標、仕組みがあると理解しています。しかし、自社システム構築、パッケージソフト開発に対しては、無駄が多く適していないように感じています。そこで、スクラムを自社システム開発、パッケージソフト開発、生成AI利用開発の３つの事例に分けて、スクラムでは不要な事項を４つ、スクラムには書いてない項目を４つ、それぞれ記載してください。
A1 by chatGPT

はい。かなり重要な視点だと思います。

まず整理すると、**Scrum Guideは「開発プロセス全体を定義する規格」ではなく、経験主義によって複雑なプロダクト開発を検査・適応するための最小限のフレームワーク**です。2020年版では、Product Goal、Sprint Goal、Definition of Done、Product Backlogなどを中心に、透明性・検査・適応を実現する構成になっています。([スクラムガイド][1])

したがって、ご指摘の

> **「ウォータフォール/CMMからアジャイルへ移行するための仕組みとしては有効だが、開発対象によってはScrumそのものを全部適用すると過剰ではないか」**

という見方は、かなり整理しやすいと思います。

ここでは「Scrumに書いてあるが、その開発では必ずしも必要でないもの」と「Scrum Guideには明示されていないが、実際には重要になるもの」を分けます。

---

# 1. 自社システム開発

例えば、

* 社内業務システム
* 生産管理
* 勤怠・人事
* 社内データベース
* 社内Webシステム

などです。

### Scrumでは不要になりやすい4項目

| # | Scrum的な仕組み                           | 自社システムでは不要になりやすい理由                   |
| - | ------------------------------------ | ------------------------------------ |
| 1 | **Product Ownerを独立した役割として置く**        | 利用部門・情報システム部門・経営層が直接意思決定できる場合が多い     |
| 2 | **毎SprintごとのProduct Increment中心の開発** | 業務上、ある程度まとまった機能単位でリリースした方が合理的な場合がある  |
| 3 | **Product Backlogを細かく分解・並べ替える活動**    | 法令、社内規則、既存業務フローなどで開発順序がほぼ決まっている場合がある |
| 4 | **Scrum MasterによるScrum運営**           | 小規模な社内開発なら、チーム自身が会議・改善を運営できる         |

Scrum Guide自身も、Scrum Masterなどを「職務記述書」ではなくaccountabilityとして扱っています。つまり、これらを組織上の固定ポストとして置くことまで要求しているわけではありません。([スクラム.org][2])

### むしろScrum Guideに書かれていない重要事項

| # | 自社システム特有の事項        | なぜ重要か                       |
| - | ------------------ | --------------------------- |
| 1 | **既存業務との整合性**      | システムだけ改善しても業務が変わらなければ効果が出ない |
| 2 | **データ移行・マスタ移行**    | 新旧システムの切替時に最大のリスクになりやすい     |
| 3 | **社内規程・法令・監査への適合** | 自社システムでは「動けばよい」ではない         |
| 4 | **運用・保守・教育・引継ぎ**   | 開発終了後の利用期間の方が長い             |

つまり自社システムでは、

**Scrumの「開発プロセス」より、業務＋システム＋運用のライフサイクル**

を管理した方が重要になることがあります。

# 2. パッケージソフト開発

これは自社システムとはかなり違います。

例えば、

* CAD
* IDE
* 業務パッケージ
* 組込み開発ツール
* SaaS
* ライブラリ

などです。

ここでは「誰か一社の要求を満たす」より、**多数の利用者にとって製品として価値があるか**が重要です。

### Scrumでは不要になりやすい4項目

| # | Scrum的な仕組み                               | パッケージ開発で不要になりやすい理由                       |
| - | ---------------------------------------- | ---------------------------------------- |
| 1 | **毎Sprintで利用可能な機能をユーザーに提供することへの過度なこだわり** | 内部アーキテクチャ変更や基盤開発など、短期ではユーザー価値にならない作業がある  |
| 2 | **Product Backlogの細かな要求単位管理**            | 技術ロードマップ・製品系列・バージョン計画の方が重要になる            |
| 3 | **Sprint単位で全ての開発活動を閉じること**               | コンパイラ、OS、DB、通信プロトコルなどでは長期的な技術開発が必要       |
| 4 | **Scrumイベントを一律に実施すること**                  | チームの成熟度が高ければ、会議を減らしてGitHub等の実績で透明性を確保できる |

Scrum Guideは、イベントを「検査と適応のための正式な機会」としていますが、同時にScrum自体を必要最小限のframeworkとして位置付けています。([スクラムガイド][1])

### Scrum Guideに書かれていない重要事項

| # | パッケージ特有の事項        | 内容                          |
| - | ----------------- | --------------------------- |
| 1 | **製品アーキテクチャ**     | API、ABI、データ形式、互換性など         |
| 2 | **後方互換性**         | Version N → N+1で既存ユーザーを壊さない |
| 3 | **リリース・バージョン戦略**  | LTS、メジャー/マイナー、deprecatedなど  |
| 4 | **市場・競合・価格・販売戦略** | 「何を作るか」だけでなく「誰が買うか」         |

ここでは、

> **Product Backlog → Sprint → Increment**

だけではなく、

> **Architecture → Product Line → Release → Compatibility → Market**

という軸が必要になります。

# 3. 生成AI利用開発

ここが一番面白いところです。

例えば、

> 人間が仕様を書く
> ↓
> 生成AIにコードを生成させる
> ↓
> AIにテストを書かせる
> ↓
> AIにレビューさせる
> ↓
> 人間が修正
> ↓
> GitHubに保存

という開発です。

この場合、Scrumの「人間チーム」をそのまま前提にすること自体が変わってきます。

### Scrumでは不要になりやすい4項目

| # | Scrum的な仕組み                   | 生成AI開発での問題                            |
| - | ---------------------------- | ------------------------------------- |
| 1 | **人間だけで構成されたDeveloper Team** | AIエージェントが実際の実装・テスト・レビューを行う            |
| 2 | **Daily Scrumによる進捗共有**       | Git commit、CI、AIログ、Issue等から進捗を自動取得できる |
| 3 | **人間によるBacklog Itemの手作業分解**  | AIが仕様→タスク→コード→テストまで分解できる              |
| 4 | **Sprint単位での人間による検査**        | AIによる継続的なテスト・静的解析・検証が可能               |

これはScrumを否定するというより、**「人間だけがDeveloperである」という前提が崩れてきた**という問題です。

2020 Scrum Guideはかなり一般化されており、「developers」はソフトウェア開発者だけを意味しないように説明されていますが、それでも生成AIエージェントそのものを開発主体として定義してはいません。([スクラム.org][3])

---

## そして生成AI開発では、Scrumにない4項目が非常に重要

| # | 生成AI開発に必要なもの           | 内容                          |
| - | ---------------------- | --------------------------- |
| 1 | **Prompt/Contextの履歴**  | どんな指示・資料・制約から結果が生成されたか      |
| 2 | **AI生成物の原文保存**         | AIが最初に生成したコード・設計・テストを消さずに保存 |
| 3 | **AI出力と人間修正の差分**       | AI→人間→AI→人間という改善過程を記録       |
| 4 | **AI自身による自己評価・再生成の履歴** | 「なぜAIが前回より良い結果を出したのか」を検証する  |

これは、先ほどお話しされていた

> **「生成AIの結果をそのまま保存し、AI自身の自律的な改善と、人間が意図的に行う改善を競わせる」**

という考え方と非常に相性がよいです。

# 4. 3種類を並べるとかなり違う

|             | 自社システム   | パッケージ      | 生成AI開発           |
| ----------- | -------- | ---------- | ---------------- |
| 主な相手        | 社内利用者    | 市場の利用者     | 人間＋AI            |
| 重要なもの       | 業務適合     | 製品価値       | 生成過程の透明性         |
| Scrumの過剰部分  | Sprint運営 | Sprint中心主義 | 人間中心主義           |
| 重要な非Scrum項目 | データ移行    | 互換性        | Prompt/Context履歴 |
| 成果物         | 業務システム   | 製品         | コード＋生成履歴         |
| 評価          | 業務効果     | 市場・利用価値    | 品質＋生成効率＋再現性      |

# 5. 私ならScrumを「4層」に分解します

ここが、従来のCMM/CMMI → Agileという議論を一段進められるところだと思います。

```text
             開発対象
                │
       ┌────────┼────────┐
       ↓        ↓        ↓
    自社システム  パッケージ  生成AI
       │        │        │
       └────────┼────────┘
                ↓
        ┌─────────────┐
        │ 共通する最小核 │
        ├─────────────┤
        │ 透明性        │
        │ 検査          │
        │ 適応          │
        │ 小さな実験    │
        └─────────────┘
                ↓
       開発対象固有の仕組み
```

つまりScrumの本質を、

**「Sprintをやること」**

から

**「透明性 → 検査 → 適応を短いフィードバックループで回すこと」**

へ戻して考えると、かなり応用範囲が広がります。Scrum Guide自身も、この3本柱をScrumの基礎として説明しています。([スクラムガイド][1])

## 特に生成AIでは「Scrum 2.0」のような考え方ができそうです

私はむしろ、

```text
従来の開発

要求
 ↓
人間
 ↓
設計
 ↓
人間
 ↓
コード
 ↓
テスト
 ↓
人間による評価
```

から、

```text
生成AI開発

要求
 ↓
┌───────────────┐
│ AI             │
│ 生成→評価→修正 │
└───────┬───────┘
        ↓
     成果物保存
        ↓
   人間による評価
        ↓
   意図的な改善
        ↓
     再生成
        ↓
   AIの自律改善
        ↓
       比較
```

という**「二重の改善ループ」**にした方が面白いと思います。

これはScrumの単なる「AI版」ではなく、

> **人間の経験主義による改善 + AIの経験主義による改善**

を比較可能にする仕組みです。

そして、ここにGitのbranch/commitを使えば、

**AI-generated branch**
vs.
**human-improved branch**

として、生成AI利用そのものを測定可能にできます。

Scrum Guideが重視する透明性・検査・適応を残しながら、Sprint、Daily Scrum、Product Backlogなどを必要な範囲だけ採用する、という設計です。([スクラム.org][2])

この考え方は、以前話されていた**「生成AIの結果を消さずに全部保存する」**という発想と組み合わせると、かなり具体的な**「生成AI時代の開発プロセス評価法」**に発展させられると思います。
